# Scoped support reports

Proposed design for [TerminalX #1246](https://github.com/terminalx-ai/terminalx/issues/1246). The report flow depends on a product decision in PRO-142 and a companion change in `terminalx-saas`. The support queue, policies, and limits below are proposed for approval.

## Desktop design and support ownership

Use one in-app support form from desktop Settings → About and the Help menu, and from mobile Settings. Propose a facts-first local diagnostics page for PRO-142, with health checks and fix actions handled as a separate design decision. The support form has a source selector and a preview. It excludes screenshots, raw log attachments, environment values, and hashes of environment values. Record these choices and the changes to the feedback mockups in PRO-142 before building the shared desktop entry point. [PRO-142 design hold](https://linear.app/procyonlabs/issue/PRO-142/add-a-local-diagnostics-page-with-json-export-and-a-send-feedback-link)

Use a private queue in TerminalX SaaS. TerminalX Support would own triage and staff access, and the SaaS team would own deployment, storage, and deletion. Name both owners before rollout. The existing sign-in recovery flow has a verified inbox, but accepts unauthenticated requests and reports acceptance by an email provider. Keep that endpoint for sign-in recovery. Scoped reports require the signed-in user's authority and a destination that can enforce deletion and audit reads. [Sign-in report delivery verification](https://github.com/dudhatparesh/terminalx-saas/issues/229)

## User flow and consent

1. Open the form. Describe the problem using a feature, symptom, and approximate onset. Offer an optional short description with separate consent for text the user writes and reviews themselves. Keep it out of the diagnostics collectors. Before preview and submission, reject likely credentials and personal identifiers, and tell the user to remove private details. Arbitrary private content is difficult to recognize in short text. If the explicit text-consent design is declined, ship only the structured description.
2. Select sources and an ending time with a 1-hour, 24-hour, or 7-day window. Leave diagnostics sources unselected on entry. Show which device each source comes from and require an explicit **Prepare preview** action before querying any selected source. Opening or editing the form leaves the collectors idle.
3. Show the destination, actual included fields or server source summaries, time coverage, limits, and retention. List all source statuses, including empty, omitted by choice, other device required, signed out, unauthorized, unavailable, and failed. Label truncation separately. Exact timestamps, build versions, operation references, platform, and failure codes can reveal usage patterns even after redaction.
4. **Send to TerminalX Support** submits the reviewed snapshot. Changing a selection, scope, window, or description invalidates the preview. Cancel before Send discards the draft, including any unsent notes. A server preview uses a proof bound to the authenticated subject, scope, window, and reviewed server snapshot. Preview data expires after 15 minutes and is discarded after submission. It creates no support report and stays out of operational logs. A scope or authorization change before submission invalidates the preview and requires fresh review.

When a report needs a second device, the user explicitly starts an **Add diagnostics to a report** flow on that device and enters the support reference. Both devices must sign in as the same account. The server checks report ownership and any organization scope before allowing an attachment. The second device previews and explicitly submits its own bounded snapshot using the report window. The reference alone grants no read or write access. A missing device stays marked as missing until its contribution is confirmed. Pairing a device never authorizes collection from it.

## Versioned source schemas and limits

Use UTC timestamps, a report schema version, and a schema version per source. Include capture time, requested bounds, observed coverage when known, and app/build version for each contributing device or service. Mark unavailable build information explicitly. Limit each source to its newest 100 events or 64 KiB, whichever comes first, and the whole uncompressed JSON report to 256 KiB, including later contributions. Reserve at most 1 KiB UTF-8 for separately consented problem text. Preview the exact effect of each cap. Reject out-of-window events and oversize or structurally invalid payloads at ingestion.

| Desktop app and runtime | Platform, architecture, app/runtime versions, startup incident ID, event time, startup category and phase, exit class, relay close class | Reuse the typed projection in [startup diagnostics](testing/startup-stalls.md) and the organization-scoped relay close buffer used by [cloud diagnostics](ACCOUNTS.md#cloud-diagnostics-and-export). Add the time filter and bounded projection. Where local records lack an account or device ownership boundary, report that collector as unavailable until it can enforce scope. |
| Mobile app and connection | Platform, app/build versions, event time, connection stage, path class such as direct or relay, outcome, and known failure code | Add a typed projection at the existing connection event producers. The current local buffer stores display messages and details, which can contain host names and addresses. Do not export either field. Older entries without typed event codes contribute only where their scope and schema can be verified. |
| SaaS account | Event time, allowlisted pairing action and outcome, and server-generated opaque correlation reference | The API stores pairing audit events with subject and actor identifiers, timestamps, and correlation IDs. A new query must constrain the authenticated subject's scope, enforce device grants where relevant, and project only the allowed fields. Return no raw before/after state. [Pairing audit schema](https://github.com/dudhatparesh/terminalx-saas/blob/522e6dce9772d28ce444f64ef788a34e4b00daca/apps/api/src/db/schema/accountPairingAuditEvents.ts) |

The existing endpoint is desktop-only and accepts whole-day windows. Add an exact-time, support-specific projection reachable by authenticated desktop and mobile clients. Recheck membership and owner/admin role in the selected organization and keep workspace-visibility checks. [Cloud diagnostics contract, section 22](https://github.com/dudhatparesh/terminalx-saas/blob/522e6dce9772d28ce444f64ef788a34e4b00daca/apps/api/docs/cloud-workspace-remote-runtime-contract.md#22-diagnostics-pro-38) |

Relay service and worker logs require a separate scoped query or correlation contract before they can be offered. Label those sources unavailable until such a contract exists. Never infer authority from a client-supplied account, organization, device, or operation identifier.

Build each projection from named fields and fixed enums. Validate again in SaaS and reuse existing cloud redaction as a second pass where applicable. Drop unknown fields and keep arbitrary strings out of diagnostic code fields. Exclude credentials, environment data, personal and device identifiers, network addresses, paths, repository or workspace names, prompts, terminal output, and private content. Keep internal ownership identifiers in the access-control record and out of diagnostic payloads and exports.

## Delivery, deletion, and support access

The SaaS change needs authenticated HTTPS intake for both apps, a private report store, a staff queue, audit records, and expiry and deletion jobs. Keep report bytes out of request logs and staff notifications. Desktop requests use the native data-privacy policy gate. Signed-out, unsupported, offline, or privacy-blocked clients can explicitly save or copy the reviewed redacted local projection. Explain that this does not send anything and that the user controls any exported copy.

Commit the report and its queue entry together. Only then return the support reference and show delivery confirmed. Retry uses the same server-issued submission key and payload, scoped to the authenticated account and to create or append. Check for a committed receipt before checking preview expiry so a retry after a lost reply returns the same receipt. Reuse of the same key with different input fails visibly. Keep proof of prior submission for a 24-hour retry window, after which the server refuses the key. If the preview expired before any commit, require another preview. Apply the byte cap to the report as a whole inside the append transaction.

At triage, staff look up the support reference in the private queue, check coverage and source statuses, and use opaque references to locate the corresponding scoped events. Require named staff accounts, a dedicated support role, a report-specific access reason, and successful audit recording before reads or correlation lookups. Audit access, append, and deletion with actor, action, reference, time, and outcome. Staff access never expands the source scope authorized for the report.

Propose 30 days from the original receipt for report data, including later contributions. A submitter can request deletion by reference through an authenticated account action. Account deletion also revokes access to and removes associated reports. Expiry and deletion purge payloads, search entries, and pending jobs, and preserve a minimal tombstone for the retry period. Retain payload-free audit records for 90 days. Before rollout, confirm backup expiry and ensure that restoration reapplies deletions before restoring staff access.

## Acceptance before rollout

- Test cross-account, cross-organization, wrong-device, wrong-scope, revoked-role, private-workspace, and staff-audit failures at the SaaS boundary. Test account deletion, expiry, and restore behavior.
- Test that opening, editing, and canceling trigger zero submissions and that collection begins only on explicit preview. Cover changed authorization, partial sources, empty windows, expired previews, and offline export.
- Seed each projection and the intake validator with credentials, environment values, personal identifiers, raw connection messages, prompts, and terminal output. Verify exclusions in previews, exports, the stored report, and operational logs.
- Exercise time and size boundaries, concurrent appends, lost replies, failed queue commits, retries, and receipt recovery. Verify a single queue receipt for each submitted contribution.
- Submit synthetic reports from supported desktop and mobile builds against staging. Attach a second device, confirm a matching reference in the staff queue, verify an audit record, and delete the test report. [PRO-456 physical-device evidence](https://github.com/terminalx-ai/terminalx/issues/1206) is a separate acceptance item.
